# Dashboard — Frontend

## Route
`/app/dashboard` → `src/pages/DashboardPage.tsx`, rendered inside `AppLayout`'s `<Outlet/>`. `/app` (index) redirects here via `<Navigate to="dashboard" replace />` in `App.tsx`.

## Component structure
`DashboardPage()` is one file with a local `Card` helper component at the top (`className` passthrough wrapper for the bento-grid tiles).

## Data fetching (real, no more hardcoded arrays)
```ts
const [data, setData] = useState<DashboardSummary | null>(null)
useEffect(() => {
  api.get<DashboardSummary>('/dashboard/summary').then(setData).catch(...)
}, [])
```
`DashboardSummary` (see `src/lib/api.ts`) is the single aggregated response from `GET /api/dashboard/summary` — see backend.md. Renders a "Loading dashboard…" state until it resolves, and an inline error if the API is unreachable.

Sections, top to bottom:
1. **Heading** — `{getGreeting()}, {data.user.name.split(' ')[0]}` + `Here's what's moving across {data.org.name} this week.`. `getGreeting()` is a local helper reading `new Date().getHours()` on the viewer's own clock — before 12 → "Good morning", before 18 → "Good afternoon", else "Good evening". Previously hardcoded to always say "Good morning" regardless of actual time; fixed per direct request.
2. **Your projects row** — `data.projects` (top 4 by `updated_at`, real). "See all →" links to `/app/projects`. The dashed "+ New project" add-tile that used to sit at the end of this row **was removed** per direct user request — creating a project now only happens from the Projects page (see `projects/frontend.md`). Each card shows the status dot + name, `docCount` + relative-update-time line, an **owner row** (small initials avatar + name, added per direct request — see `dashboard/backend.md`), and the status label. Same avatar styling as the Projects page's own cards, just smaller (`h-4 w-4` vs `h-5 w-5`) to fit this row's more compact `min-w-[196px]` tiles. Each card is now a `<button>` (was a plain, non-interactive `<div>`) that opens a read-only details panel — see "Read-only project panel" below.

### Read-only project panel (as built)
Direct request: "each project on the dashboard needs to be clickable so that each one view the details but it can't be editable except the owner." First version made the cards `<Link to="/app/projects?open=<id>">`, navigating away and opening the shared edit/view drawer over there (see `projects/frontend.md`). Undone on direct follow-up — "why it is redirecting to the project project. It needs to on the same page and the details need to be visible on the view mode only" — the Dashboard needed its own self-contained view, not a hop to another page. Noted here (and in `projects/frontend.md`) so the reverted approach isn't rebuilt from stale memory.

Cards are now `<button onClick={() => setViewProjectId(p.id)}>`. A `viewProjectId` state (the clicked project's id, or `null`) drives a `useEffect` that fetches `GET /projects/:id` (the same endpoint the Projects page uses, previously otherwise unused by any frontend route — see `projects/backend.md`) into a `viewProject` state. The panel itself reuses the exact right-drawer convention established by `ProjectsPage.tsx`'s own drawer (`ChatDrawer.tsx`'s pattern — always mounted, `translate-x-0`/`translate-x-full` toggled by whether a project is selected) — same visual language across the app, not a third variant.

**Unconditionally read-only — no `canEdit` check at all, unlike the Projects page's drawer.** There's no editing entry point on the Dashboard whatsoever, for anyone, including the owner — "the details need to be visible on the view mode only" was explicit. Rather than reusing `ProjectsPage.tsx`'s form (inputs/selects, just always `disabled`), the panel renders plain label+value blocks via a small `DetailRow` helper — real `<div>`s, not disabled form controls, since a disabled `<input>` still visually implies "this could be edited if you were allowed to," which isn't true here even for the owner. Shows: status pill + docs/updated line, description, owner (avatar + name), Git URL, Deployment URL, Username, Password — same field set the Projects page's view-only mode shows, for consistency between the two read-only surfaces. Only a "✕" close button; no Cancel/Save row, since there was never anything to cancel or save.

## Task calendar + Leave calendar (as built)
Direct request: "Add a task calender showing the task count of the individuals per date and a leave calender on the dashboard page showing the persons on leave." Both cards were appended at the end of the bento grid, each built around a hand-rolled month grid rather than reusing `DateRangePicker`'s `react-day-picker` — consistent with how "Next event"'s week strip already builds its own 7-cell calendar by hand rather than pulling in the picker library, since neither needs picking, just display.

**Initially `col-span-2` (full width) each**, stacked one above the other — direct follow-up, "Can you keep the task calender and the leave calender in a single line instead of 2," dropped both `col-span-2` classes so they fall back to the grid's normal single-column sizing and land side by side in one row (same `grid-cols-2` bento grid every other card already sits in — no new wrapper needed, removing the span was enough). The 7-day grid inside each card is unaffected — narrower cards just mean narrower day cells, still legible up to the existing 2-chip-then-"+N more" cap.

A new `getMonthGridDates(date)` helper (alongside the existing `getWeekDates()`) returns a `(Date | null)[]` — `null` for the blank cells before day 1 and after the last day of the month, padded so the array always divides evenly into 7-wide week rows. Both cards render the same Sun–Sat header row, then `.map()` over the grid: a `null` cell renders an empty `<div>` (keeps the grid alignment without a visible box), a real date renders a bordered cell, sized `min-h-[62px]` to fit a couple of stacked entries. `toDateOnly()` (the same local-date `'YYYY-MM-DD'` helper already used for holiday-date matching) keys into a `Map` built from `taskCalendarDays`/`leaveCalendarDays` — component state fetched per calendar (see "Month navigation" below), not read off the initial `data` summary. Today's cell gets the accent border/background treatment (`border-accent bg-accent-tint`), same visual language as the event-day highlight in "Next event" — computed from the real `new Date()`, independent of whichever month is currently *displayed*.

**Task calendar**: each populated day shows up to 2 "`initials` ×`count`" chips (`byAssignee`, already sorted busiest-first by the backend), and a "+N more" line if a date has more than 2 assignees with tasks due — the full breakdown for every assignee on that day is still available via the cell's `title` attribute (a native browser tooltip on hover), so nothing is actually hidden, just not all rendered as chips in a ~62px cell. "See all →" links to `/app/tasks`.

**Click a date to see the actual tasks**, direct follow-up: "Clicking on the particular date, it needs to show the tasks for the same date." Each day cell in the Task calendar is a real `<button>` now (was a `<div>`), `disabled` when it has no tasks (`hasTasks = assignees.length > 0` — an empty day isn't clickable, no `cursor-pointer`/hover styling either, so it doesn't invite a click that would just show "nothing here"). Clicking a populated day sets `selectedTaskDate` (`'YYYY-MM-DD'`) and opens a centered modal (same overlay/box convention as `ReasonModal.tsx` — `fixed inset-0 bg-ink/25` + a centered `rounded-2xl` card, `z-[200]`/`z-[201]`), closable via its own `✕` or by clicking the overlay.

The modal doesn't reuse `taskCalendar`'s data — that only has per-assignee *counts*, not task titles — so a `useEffect` keyed on `selectedTaskDate` fetches the real list from the existing `GET /api/tasks?filter=open&dueFrom=<date>&dueTo=<date>` endpoint (already supported by `tasks.ts` for date-range filtering, reused here for an exact single-day range rather than adding a new endpoint or growing `taskCalendar`'s payload for a rarely-opened detail view). Each row in the modal shows the task title, assignee (avatar chip + name, or "Unassigned"), and the meeting it came from — the same fields `TasksPage.tsx` already shows per task, just scoped to one day. A `formatCalendarDate()` helper (same "build the Date from the string's parts" pattern as `formatHolidayDate()`) renders the modal's heading as a full weekday + date, e.g. "Tuesday 4 August."

**Month navigation (as built)**: direct follow-up — asked "why there is no previous/next month option," confirmed wanting it added. Each calendar now tracks its own displayed month independently: `taskCalendarMonth`/`leaveCalendarMonth` (`Date`, always normalized to the 1st of the month) plus `taskCalendarDays`/`leaveCalendarDays` (`TaskCalendarDay[] | LeaveCalendarDay[] | null`, `null` while loading). A `‹`/`›` button pair and a "Month Year" label (`toLocaleDateString(undefined, { month: 'long', year: 'numeric' })`) sit between each card's header and its weekday row; clicking either calls `setTaskCalendarMonth((m) => shiftMonth(m, ±1))` (a new helper, returns the 1st of the month `delta` months away). A `useEffect` keyed on each month state re-fetches from the new dedicated endpoints — `GET /dashboard/task-calendar?month=<monthKey>` / `GET /dashboard/leave-calendar?month=<monthKey>` (`monthKey()`: `'YYYY-MM'`) — instead of reading `data.taskCalendar`/`data.leaveCalendar` off the summary response, which no longer carries them at all (see `dashboard/backend.md`'s "Month navigation" section for why this became two dedicated endpoints instead of a `?month=` param on `/summary`). This applies even to the initial "this month" view — there's one code path for "load a month's calendar," not a special case for the default month plus a different one for navigated months. Each card shows "Loading…" in place of its day grid (weekday header stays put) while its own `*CalendarDays` is `null`, mid-fetch.

The two calendars navigate fully independently — moving Task calendar to July doesn't touch Leave calendar's month, and vice versa, since each owns its own state and effect.

## Known gaps
- No "+6%" / "+12%" trend deltas — would need periodic snapshots of the aggregate numbers to diff against (e.g. a nightly job writing to a `dashboard_snapshots` table).
- "+ New project" button (top bar, shared via `AppLayout`) was moved to the Projects page and still has no `onClick` — see `projects/frontend.md`.
- ~~"🔔" notification bell button is still decorative~~ — no longer true, see `notifications/backend.md` and `notifications/frontend.md`.
- Next event's mini calendar only shows the week containing the event — if the next event is more than ~6 days out, there's no indication of "how far" beyond the date number itself (no "in 5 days" label).
- (Historical, no longer visible in the UI — see the "Removed later" note above) "Today's meeting update" was misleadingly named — it was really "most recently logged meeting," not specifically something that happened today. "Most popular content" was driven entirely by Ask The Record citations — a document nobody's asked about yet, however important, would never show up there even if it was the most-updated or most-referenced-in-conversation doc in spirit. Kept here since `GET /api/dashboard/summary` still computes and returns both fields (see `dashboard/backend.md`), so these caveats still apply if either is ever surfaced again.
- `getGreeting()` uses the viewer's own local browser clock, not the org's timezone or the server's clock — correct behavior for a single-viewer greeting, just worth knowing if this ever needs to match a specific org-wide "business hours" definition instead.
- Task calendar only counts *open* tasks — a day where someone finished 5 tasks shows nothing, since the calendar is meant as a forward-looking capacity view, not a completed-work log.
- A day cell with more than 2 (task calendar) or 3 (leave calendar) people collapses the rest into "+N more"/"+N" — the full list is only reachable via hover tooltip, not a click-to-expand, so it's not touch-friendly on a mobile viewport.
- Only the Task calendar's day cells are clickable — the Leave calendar's are still plain (non-interactive) `<div>`s, so there's no equivalent "click a day to see who's on leave, with reasons" detail view yet, only the hover tooltip.
- Month navigation has no bounds and no "jump to today" shortcut — you can page arbitrarily far into the past or future, and the only way back to the current month is clicking `‹`/`›` the whole way, one month at a time.
- Each calendar's displayed month resets to the current month on every page load/reload — there's no URL param or persisted state remembering "I was looking at September" across navigations away from and back to the Dashboard.
