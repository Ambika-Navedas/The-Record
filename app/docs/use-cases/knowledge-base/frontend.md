# Knowledge Base — Frontend

## Routes
- `/app/knowledge` → `src/pages/KnowledgePage.tsx` (list), inside `AppLayout`.
- `/app/knowledge/trash` → `src/pages/KnowledgeTrashPage.tsx` (trash view), inside `AppLayout`. Registered *before* `knowledge/:id` in `App.tsx` for readability, though React Router v6 would rank the static segment over the dynamic one regardless of declaration order.
- `/app/knowledge/:id` → `src/pages/KnowledgeDetailPage.tsx` (detail — full excerpt), also inside `AppLayout`. New; previously rows weren't links at all and `GET /api/knowledge/:id` (which already existed) had no frontend caller.

## Component structure
Single-file page.

- `typeIcon` / `typeLabel` — still maps all six types (`sop`/`meeting_note`/`decision`/`faq`/`email`/`file`) to an emoji icon and a display label, even though three no longer have filter chips (see below) — a doc of any type still renders correctly in the "All" tab if one ever exists (`email` → 📧, added for Gmail sync; `file` → 📎, added for project-creation document uploads — see below).
- `filters` — `[{key:'all',...}, {key:'meeting_note',...}, {key:'email',...}, {key:'file',...}]`. Originally also had `sop`/`decision`/`faq` chips; removed by direct request ("Remove these from the knowledge base," pointing at the `SOPs · 0`/`Decisions · 0`/`FAQs · 0` chips) since nothing in this app ever creates those types — `POST /knowledge` (the only endpoint that could) has no frontend caller, so the three chips always read `· 0`. **Backend/schema untouched** — `knowledge_documents.type`'s CHECK constraint still allows `sop`/`decision`/`faq`, and `GET /knowledge?type=` still accepts them as a query value; only the chip buttons that filtered by them are gone. If a document of one of those types is ever created directly via the API, it still shows up under "All" with the correct icon/label — it's just not filterable to on its own via a chip anymore.
- `dateFilters` — `[{key:'all',...}, {key:'today',...}, {key:'week',...}, {key:'month',...}]`, replacing the old `sortOptions`/`typeSortWeight` client-side sort entirely — see "Date filter" below.
- `formatDate(iso)` — renders an absolute date (`"Aug 3"`) rather than a relative one. Was `timeAgo(iso)` (the "same pattern as Projects/Dashboard" relative-time helper this line used to describe) until a direct request to show the actual date on each row instead of "Updated 3d ago" — replaced outright rather than kept alongside, since nothing else in this file used it. The leading `Updated ` label was later dropped too, per direct request, once the freshness dot next to it made the word redundant — the date sits bare next to the dot now.

## Date filter (replaces the old client-side Sort control)
The `Sort: Recently updated ⌄` control (a real native `<select>` doing client-side re-sorting — `updated_desc`/`title_asc`/`type`, added earlier this session) was removed outright per direct request and replaced with a **real, server-side date filter** in the same UI slot. This isn't a naming tweak — the old control reordered an already-fetched list client-side; the new one requests a genuinely smaller result set from the backend (`GET /knowledge?type=&from=&to=`, see backend.md), so the row count and every type-chip's count change with it, not just the row order. Sorting itself didn't go away — the list is still always most-recently-updated-first, just fixed server-side (`ORDER BY kd.updated_at DESC`, unconditional) rather than user-adjustable, the same tradeoff already made for `TasksPage.tsx` (see `meetings/frontend.md`).

This went through two iterations. First: a `Date: All time|Today|This week|This month|Custom range…` `<select>`, with two native `<input type="date">` fields appearing when "Custom range…" was picked. Verified live at that point: "This week" narrowed 24 items to 3, custom `2026-07-20`–`2026-07-31` narrowed to 6, both cross-checked against curl.

**Then replaced again** by direct request for something matching a reference screenshot of a full calendar-dropdown range picker (dual-month grid, preset sidebar, popover trigger) — see `components/DateRangePicker.tsx` below. `KnowledgePage.tsx`'s `dateFilter`/`dateFrom`/`dateTo` state collapsed into one `dateRange: DateRangeValue | null`, and the whole `<select>` + conditional inputs block became a single `<DateRangePicker value={dateRange} onChange={setDateRange} placeholder="All time" />`. `fetchKnowledge()` sends `from`/`to` only when `dateRange` is set — no filter param at all means no date narrowing, same "presence-based, not an enum" simplification made on the backend (see backend.md).

## `DateRangePicker` (`src/components/DateRangePicker.tsx`)
A reusable calendar-dropdown range picker — trigger button (`📅 <range or placeholder> ⌄`) + popover with a preset sidebar (All time / Today / Yesterday / Last 7 days / Last 30 days / Last 3 months) and a two-month `react-day-picker` range calendar. Used here and twice more on `TasksPage.tsx` (Meeting date, Due date — see `meetings/frontend.md`). `value`/`onChange` use the same `{ from, to }` `'YYYY-MM-DD'` string shape every call site already worked with; the component only converts to/from real `Date` objects internally for `react-day-picker`'s benefit (`toDateOnly`/`fromDateOnly`, using local-time formatting, not `toISOString().slice(0, 10)`, which converts to UTC first and can shift the date by one near midnight in timezones behind UTC).

**`react-day-picker`** (`^10.x`) is the first UI dependency this app has ever had — everything before this was hand-rolled native controls (`<select>`, `<input>`) styled with Tailwind. Chosen over hand-rolling the calendar/range math after weighing it against the size of the ask: a dual-month range calendar with drag-select is real component work to get right (leap years, week-start locale, keyboard nav, accessible date buttons), and `react-day-picker` is actively maintained with first-class React 19 support, unlike some older alternatives in this space.

**Popover positioning was the hard part**, and went through three attempts:
1. `left-0` (popover's left edge = trigger's left edge) — fine for triggers on the left of a page, but the Knowledge Base trigger sits near the far right of its row, so the ~730px-wide popover overflowed off the right edge of the viewport entirely (invisible, not just clipped).
2. Fixed `right-0` — fixed Knowledge Base, but then Tasks' more centrally-positioned "Meeting date" trigger overflowed off the *left* edge instead. No single fixed side works for every call site.
3. **What shipped**: render at `left: 0` first, then in a `useLayoutEffect` (runs before paint, so no visible flicker) measure the popover's actual rendered `getBoundingClientRect()` and apply a `translateX` correction if it overflows either edge, clamped to an 8px margin. This is a real measurement of the real rendered box, not a guess about the popover's width ahead of time — which mattered in practice, since Tasks packs three filters (Assignee, Meeting date, Due date) into one row tightly enough that neither a pure left- nor pure right-anchor had enough room on *either* side for the rightmost ("Due date") trigger at a standard 1280px viewport; only a per-pixel correction handled that case correctly.

Also needed `flex-shrink-0` on the `DayPicker`'s own root (its default flex-basis let the two-month grid shrink and wrap onto two rows instead of sitting side by side) and removing `overflow-hidden` from the popover's outer container (it was clipping the second month's rendered content, which was otherwise positioned correctly — replaced with `rounded-l-xl` on the preset sidebar directly, so the rounded-corner look survives without clipping anything).

**Sized down further** per direct follow-up report that the calendar was too large relative to the page. `react-day-picker`'s default day-cell size is 44px (`--rdp-day-width`/`--rdp-day-height`) with 42px click targets and a 2rem gap between the two months — comfortably legible but wide (~800px popover at default size). Passed a smaller set of the same CSS custom properties via the `DayPicker`'s `style` prop (34px cells, 32px click targets, 1.25rem month gap, smaller nav buttons) plus a `text-[13px]` base font and a smaller `month_caption` class, shrinking the whole popover by roughly 100px without needing to touch the sidebar or trigger button. `react-day-picker` documents all of these as intended per-instance overrides (not an internal implementation detail this fights against), so this is a supported customization, not a hack.

**Range highlight simplified** right after, per direct report that a selected range still "looked so big." Root cause wasn't the cell size (just fixed above) — it was `react-day-picker`'s default `--rdp-selected-border` (`2px solid var(--rdp-accent-color)`), which its base CSS applies to *every* day inside a selected range via `.rdp-selected .rdp-day_button`, not just the two endpoints. With range mode, every in-between day counts as "selected," so a 5-day range rendered as five individually-outlined circles chained together — visually heavy, not a clean bar. Set `--rdp-selected-border: 'none'` in the same `style` prop; the two endpoints stay visually distinct on their own via the existing `range_start`/`range_end` solid-fill classNames, and the days between them now render as a single flat `bg-accent-tint` bar with no per-day ring.

**Then the range-middle text itself was still bold**, per a direct follow-up ("don't make it bold, just highlight it") — a second symptom of the same root cause: `.rdp-selected { font-weight: bold }` applies to every in-range day too, not just the border. Added `font-normal` to the `range_middle` className, plus the same to `range_start`/`range_end` for consistency when a follow-up ("don't bold the selected date range") reported the endpoints still looked bold too.

**That `font-normal` didn't actually work** — reported a third time as still bold. This time, instead of tweaking the class again on assumption, checked the *computed* style directly (`getComputedStyle(dayButton).fontWeight`) rather than trusting a screenshot: it read `700` even though `font-normal` was correctly present in the element's class list. Root cause: CSS **source order**, not specificity — `react-day-picker/style.css` is imported inside `DateRangePicker.tsx` itself, which Vite bundles *after* the app's global Tailwind stylesheet (imported once at the app root), so at equal specificity (`.rdp-selected` vs `.font-normal`, both single-class selectors) the library's later-loaded rule always won regardless of which elements had `font-normal` in their class list. Switched to Tailwind's `!font-normal` (generates `font-weight: 400 !important`) on all three (`range_start`/`range_end`/`range_middle`), which can't lose to source order. Re-verified the same way — `getComputedStyle` now reads `400` on both a range-middle day and the range-start day — not just a screenshot that happened to look right.

**One more symptom of the exact same rule**: reported that selected dates still looked "bigger." `.rdp-selected` in `react-day-picker`'s base CSS sets `font-size: large` right alongside `font-weight: bold` — the same rule, two properties, and only one had been overridden. Added `!text-[13px]` next to `!font-normal` on all three classNames (same `!important` reasoning — a plain `text-[13px]` would lose the same source-order fight the plain `font-normal` did). Verified via `getComputedStyle` on a range-middle day, the range-start day, and an unselected day side by side: all three now read `fontSize=13px, fontWeight=400` — genuinely identical, not just visually close.

Verified live at 1280px and 1600px viewports, for all three trigger positions (Knowledge Base's Date filter, Tasks' Meeting date, Tasks' Due date): every popover renders fully on-screen, both months visible side by side, presets narrow correctly (e.g. "Last 7 days" → 5 items, matching a direct API check), manual two-click range selection on the calendar grid itself (not just presets) correctly highlights the range and filters (e.g. clicking Aug 4 then Aug 8 narrowed to 3 items with the trigger showing "8/4/2026 → 8/8/2026"), and after the size reduction the popover now sits with visible margin from the viewport edge at 1280px rather than nearly touching it.

## Data fetching (real, server-filtered)
```ts
useEffect(() => {
  setData(null)
  api.get<{ items, counts }>(`/knowledge?type=${filter}`).then(setData).catch(...)
}, [filter])
```
Both the list and the chip counts (`Emails · 27`, etc.) come from `GET /api/knowledge?type=` (see backend.md). The old client-side `src/data/knowledgeBase.ts` mock (12 hardcoded entries) **has been deleted** — this page and the Ask The Record chat now both read from the same real `knowledge_documents` table server-side, so they can never disagree about what documents exist.

## Freshness indicator — now real
The old `freshUpdates` string-matching hack (`Set` of exact `updated` strings like `'2 hours ago'`) is gone. The server now computes `isFresh` as a real boolean: `updated_at` within the last 24 hours (see backend.md's `FRESH_WINDOW_HOURS`), returned directly in the API response as `doc.isFresh`.

## Gmail sync bar
A card above the filter chips (`Sync emails from: ...`), fetched once on mount from `GET /api/integrations` (the same endpoint the Meetings page's Zoom/Google Meet sync bar uses — `gmail` is just a third key in the same response). Same visual states as the Meetings page's bar: **not configured** (grey, tooltip pointing at `server/.env.example`), **Connect Gmail** (plain `<a href>` navigation, not `fetch` — same reasoning as the other OAuth connect links), or **Gmail connected** with an inline **Disconnect**.

Once connected, two more controls appear that the Meetings page's bar doesn't have:
- **Search query input** — a text field bound to local state (`gmailQuery`), initialized from `integrations.gmail.query` on load. Required because, unlike meeting sync, there's no reasonable default scope for an inbox (see backend.md). Placeholder text (`label:clients or from:*@acme.com`) hints at Gmail's own search syntax, which the query is passed through to verbatim.
- **Save button** — `PUT /integrations/gmail/query`, disabled when the input matches what's already saved (`gmailQuery.trim() === gmail.query`) so it doesn't look clickable when there's nothing to save.

**Sync now** is disabled until `gmail.query` (the *saved* value, not just what's typed) is non-empty — you have to Save before you can Sync, so a half-typed, unsaved query can't be silently used. Calls `POST /integrations/gmail/sync`, shows a banner with the imported count, then refetches the knowledge list.

**Post-OAuth banner**: same pattern as Meetings — reads `?integration=gmail&status=connected|error` from the URL on mount, shows a dismissable banner, strips the params via `history.replaceState`. The backend redirects here (`/app/knowledge`) rather than `/app/meetings` after the Gmail OAuth round trip, since Gmail's home is the Knowledge Base page, not Meetings.

## Knowledge detail page (KnowledgeDetailPage.tsx)
Fetches `GET /knowledge/:id` on mount (via `useParams<{ id }>()`) — same `serialize()` shape as list items, so no new backend work was needed, just a frontend page that finally calls an endpoint that had existed since before Gmail sync was built. Header mirrors the list row's layout (type icon, title, type/project/owner line, freshness dot + full timestamp instead of `timeAgo()`'s relative format), followed by the excerpt in a card below, rendered with `whitespace-pre-wrap` so multi-paragraph content (email bodies especially) keeps its line breaks instead of collapsing into one run-on block.

List rows on `KnowledgePage.tsx` are now `<Link to={\`/app/knowledge/${doc.id}\`}>` instead of plain `<div>`s — same "whole row is clickable" pattern as Meetings' rows and Projects' cards. (Fixed a pre-existing typo while touching this block: `text-lmuted` → `text-muted` on the type/project/owner line — harmless since it just fell back to inherited text color, but worth noting since it was invisible until someone looked at the class list directly.)

### File documents (`type='file'`, as built)
`doc.hasFile` (true whenever `fileName !== null`, see `knowledge-base/backend.md`) branches the content card into a distinct layout instead of the excerpt/empty-state one every other type uses: a 📎 icon tile, the original filename + a human-readable size (`formatFileSize()` — bytes → B/KB/MB, same unit-scaling convention as `MeetingDetailPage.tsx`'s asset sizes), and a **Download** button linking directly to `${API_BASE_URL}/knowledge/${doc.id}/download` (a plain `<a href>`, not a fetch — lets the browser handle the download natively, same pattern as the meeting-asset download link). Since a `type='file'` row's `excerpt` is always empty, without this branch the page would render "No content on this document." for every uploaded file, which is technically true but not useful — the file *is* the content, just not as inline text.

### Why the email excerpt used to look truncated after clicking through
Before this page existed, `excerpt` was written by the Gmail sync (`EMAIL_EXCERPT_MAX_CHARS` in `integrations.ts`) at 500 characters — reasonable for a search-index preview, but there was nowhere to read past that limit anyway since no detail view existed. Once this page made `excerpt` something a person actually reads, 500 chars cut most real emails off mid-sentence. Bumped to 8000 chars (see `knowledge-base/backend.md`) and re-ran Gmail sync to backfill the existing 25 synced rows with the fuller content — the dedup-by-`external_id` upsert path means re-syncing updates `excerpt` on already-synced messages rather than skipping them.

### Why the excerpt card looked mostly blank on the right (as built)
Direct report, with a screenshot: an email excerpt rendered as a narrow ~530px column with a large blank area filling the rest of the (much wider) card. First guess was a CSS width cap — the paragraph had a leftover `max-w-2xl`, removed — but that changed nothing visually, which was the tell that the real cause wasn't CSS at all.

The actual cause: synced email excerpts are plain-text bodies that Gmail hard-wrapped at ~72 characters — every visual "line" in the stored text ends in a real `\n` (often `\r\n`), independent of any container width. `whitespace-pre-wrap` faithfully reproduces those breaks, so the text wrapped at the same ~72-character column no matter how wide the page was — CSS width was never the bottleneck.

Added a `reflow()` helper that runs on `doc.excerpt` before rendering (display-time only — doesn't touch the stored data, so nothing else reading the same `excerpt` field needed to change). It walks the text line by line and joins hard-wrapped lines back into the sentence/paragraph they were part of, except for lines that should stay on their own: a bullet (`- `), a forwarded-message divider (`----------`), a mail-header field (`From:`, `Date:`, `Subject:`, `To:`, detected via `/^[A-Z][\w '-]*:\s?\S/`), and — a second pass after `"Next steps Ambika"` and similar got swallowed into the previous paragraph — the literal `"Next steps "` marker these emails use for the per-person action-item sections (`meetings/backend.md`'s auto-task-extraction already keys off this exact string, so reusing it here isn't a guess). None of those four cases have a blank line before them in the source, which is exactly why a naive "collapse everything until the next blank line" pass wasn't enough on its own.

Verified live at 1440px: the "Quick recap" paragraph now flows edge-to-edge instead of down a narrow column; each mail-header field stayed on its own line; the "Next steps Ambika" / "Deepika" / "Faizan" per-person bullet sections rendered with each bullet on one flowing line and each person's name isolated above their bullets, matching how the source content actually reads.

## Trash (KnowledgeTrashPage.tsx)
Direct request: deleting a document shouldn't be a hard delete — it should move to a trash view first, recoverable, until explicitly purged from there. See `backend.md` for the soft-delete (`deleted_at`) implementation.

- Each row on `KnowledgePage.tsx` got a 🗑 icon button (`handleTrash`) alongside the existing freshness/timestamp column, inside the same `<Link>` that makes the whole row clickable through to the detail page. The button calls `e.preventDefault(); e.stopPropagation()` before the API call so clicking it moves the document to trash without also navigating to its detail page — verified live (clicking it keeps the URL at `/app/knowledge`, doesn't fire a navigation). A `<button>` nested inside the row's `<a>` (the `<Link>`) is invalid HTML5 (interactive content can't nest), but browsers render it fine and Playwright's accessibility tree still exposes it as a distinct, clickable button — confirmed via a live snapshot rather than assumed.
- A `🗑 Trash` link next to the Sort control navigates to `/app/knowledge/trash`, showing the count (`🗑 Trash · 3`) only when non-zero — mirrors the filter chips' `Label · N` pattern but stays unobtrusive (no `· 0`) when trash is empty.
- `KnowledgeTrashPage.tsx` is a new, separate page (not a filter/tab bolted onto `KnowledgePage.tsx`) since trashed items need fundamentally different actions (Restore / Delete forever) than active ones (click-through to detail, type sort/filter) — reusing the same row visuals but a plain `<div>` instead of a `<Link>` (no detail page for a trashed item).
- **Delete forever** is the one truly irreversible action in this whole feature (trashing is reversible via Restore), so it's gated behind a `window.confirm()` — the only confirm dialog in the app; every other delete/disconnect action (Gmail disconnect, meeting asset/task delete) fires immediately with no confirmation, by established convention. The exception was deliberate given the stakes are different here (permanent data loss vs. reversible or low-stakes actions).

## Known gaps
- No pagination (fine for the seeded 12 docs, though Gmail sync could push this higher — no pagination on the sync side either, capped at 25 messages per sync via `maxResults`).
- No loading/spinner state on Gmail's individual Connect/Disconnect/Save buttons — only "Sync now" shows a busy state ("Syncing…"), same gap noted for the Meetings sync bar.
- Trash has no pagination or bulk actions (restore all / empty trash) — fine at demo scale, one-at-a-time only.
- No "time until permanently auto-deleted" — trashed items stay in trash indefinitely until a person manually restores or hard-deletes them (matches the direct request: soft delete only, no auto-purge policy was asked for).
- No upload UI on this page itself — the only way a `type='file'` document gets created is through the Projects page's "New project" form (see `projects/frontend.md`), not from anywhere within the Knowledge Base. `POST /knowledge` (which would support a general "add a document" flow, with or without a file) has no frontend caller at all.
