# Meetings — Frontend

## Routes
- `/app/meetings` → `src/pages/MeetingsPage.tsx` (list), inside `AppLayout`.
- `/app/meetings/:id` → `src/pages/MeetingDetailPage.tsx` (detail — assets + tasks), also inside `AppLayout`. New; previously the "View →" links were dead `href="#"`.
- `/app/tasks` → `src/pages/TasksPage.tsx` (cross-meeting task list), also inside `AppLayout`. New nav tab, positioned right after "Knowledge Base" in `AppLayout.tsx`'s `tabs` array per direct request.

## Component structure
Single-file page.

- `filters` — `[{key:'all',...}, {key:'this_week',...}, {key:'needs_review',...}]`.
- `formatWhen(iso)` — local helper, returns `{ when: 'Today'|'Yesterday'|'Jul 26', time: '10:00 AM' }` from a real ISO timestamp.

## Data fetching (real, server-filtered)
```ts
useEffect(() => {
  setItems(null)
  api.get<{ items: MeetingItem[] }>(`/meetings?filter=${filter}`).then((res) => setItems(res.items)).catch(...)
}, [filter])
```
**"This week" now actually filters** — it's a real `WHERE scheduled_at >= datetime('now','-7 days')` query server-side (see backend.md). This was a documented gap in the old mock version (`filter === 'this_week'` fell through to showing everything); it's fixed now that there's a real backend to do the date comparison.

## Zoom / Google Meet sync bar
A card above the filter chips (`Sync meetings from: ...`), fetched once on mount from `GET /api/integrations`:
- Each provider renders one of three states: **not configured** (grey, `cursor-not-allowed`, tooltip pointing at `server/.env.example` — the server has no OAuth app credentials), **Connect {provider}** (a plain `<a href="http://localhost:4000/api/integrations/{provider}/connect">` — a real page navigation, not a `fetch`, since the point is the browser has to land on Zoom's/Google's own consent screen and come back), or **{provider} connected** with an inline **Disconnect** button (`DELETE /api/integrations/:provider`, then refetch status).
- **Sync now** button — disabled unless at least one provider is connected. Calls `POST /api/integrations/sync`, shows a banner summarizing per-provider results ("Zoom: 3 synced, 2 recordings · Google Meet: failed") — the recordings count (from the backend's new `recordingsImported` field) only appears when it's greater than 0, since most syncs won't have a finished cloud recording to pick up. Then refetches the meeting list so new/updated rows show up immediately.
- **Post-OAuth banner**: after the OAuth round trip, the backend redirects back to `/app/meetings?integration=zoom&status=connected` (or `status=error`). A one-time `useEffect` reads those query params on mount, shows a dismissable success/error banner, then strips them via `history.replaceState` so a page refresh doesn't re-show it.
- **Source badge**: meeting rows show a small pill next to the project pill — "Zoom", "Google Meet", or "From synced email" — only when `source` is one of those (manual/other meetings show nothing extra). Backed by `sourceLabel: Record<string, string>` keyed by the `source` field, which the backend only recently started including in `/api/meetings` responses (previously computed but never serialized). The `email_sync` entry (`"From synced email"`) was added alongside `meetings/backend.md`'s auto-task-extraction feature — without it, meetings auto-created from a synced summary email would silently show no badge at all rather than an error, since the badge only renders when a label exists for the source value.

## "+ New meeting" (MeetingsPage.tsx)
Top-right button next to the page heading, same placement/style as Projects' "+ New project". Opens a modal (`MeetingFormState = { title, summary, projectId, scheduledAt, durationMin }`) with a native `<select>` for project (fetched once from `GET /projects?status=all`, id+name only — no owner/status needed here), a duration number input (default `30`, step `5`), and an HTML `<input type="datetime-local">` defaulted to "now" via `toDatetimeLocal()` (a local helper that formats a `Date` as the `YYYY-MM-DDTHH:mm` string the input needs, in local time — a plain `toISOString()` would be UTC and desync the displayed value from what the user picked). Submits to `POST /meetings`, then closes and refetches the list. This was previously a backend-only endpoint with no frontend caller at all.

### Participants (as built)
Direct request, alongside adding task/meeting notifications: manual meeting creation previously collected no participant data at all — see `meetings/backend.md`'s "Participants on manual creation." A **Participants** field was added to the same modal, between "Date & time" and the error box: a scrollable (`max-h-32 overflow-y-auto`) list of checkboxes, one per org member, fetched once from `GET /users` (`orgUsers` state, reusing the `OrgUser` type already used elsewhere for owner pickers) — plain checkboxes rather than a native `<select multiple>`, since ctrl/cmd-click multi-select is non-obvious and this app already favors hand-rolled controls over relying on native multi-select semantics. `participantIds: string[]` is separate `useState`, not folded into `MeetingFormState` (which holds only single-value fields), reset alongside the rest of the form in `openCreateModal()`. `toggleParticipant(userId)` adds/removes an id from the array; the checkbox's `checked` reads `participantIds.includes(u.id)` directly rather than tracking a separate per-user boolean map. Sent as `participantIds` in the `POST /meetings` body alongside the existing fields.

### "Set up in Google Meet instead" link
A secondary text link inside the same modal, above the Cancel/Create buttons — for when what you actually want is a *real* Google Meet-linked meeting, not a manually-logged record. `buildGoogleCalendarUrl()` builds a Google Calendar ["quick add" URL](https://calendar.google.com/calendar/render?action=TEMPLATE) (`action=TEMPLATE&text=...&details=...&dates=...`) from whatever's currently typed into the form — no API call, no extra OAuth scope beyond what Calendar sync already has, since this is just a prefilled link, not a write. Clicking it opens Calendar in a new tab (`target="_blank"`) and closes our modal (`onClick` doesn't `preventDefault`, so the navigation still happens — it just also dismisses the modal since we're not creating a local record for this path).

The `dates` param needs UTC in `YYYYMMDDTHHMMSSZ` format — `fmt()` strips `-`/`:` from `toISOString()` and drops the milliseconds, computing the end time from `scheduledAt + durationMin`. Verified end-to-end: a form with title "Client sync call" and the default 30-minute duration produced `dates=20260804T121400Z/20260804T124400Z` for a `17:44` local (IST, UTC+5:30) input — correct conversion.

Once the user finishes the event in Calendar's own UI (Calendar auto-attaches a Meet link for many accounts, or they click "Add Google Meet video conferencing" themselves), that meeting shows up here automatically on the next "Sync now" — the existing Google Meet sync already picks up any calendar event with a Meet link (see `meetings/backend.md`). No new backend work was needed for the sync half; this was purely a frontend addition.

## Meeting detail page (MeetingDetailPage.tsx)
Fetches `GET /meetings/:id` (via `useParams<{ id }>()`) on mount — the response already includes `assets` and `tasks`, so this is the only fetch needed besides `GET /users` (for the task-assignee dropdown).

**Assets section:**
- Upload is a `<label>` wrapping a hidden `<input type="file">` (styled as a button — the actual file input is invisible, clicking the label opens the OS file picker). On change, builds a `FormData` with the file under the `file` field and calls the new `api.upload()` helper (`app/src/lib/api.ts`) — a separate method from `api.post()` because it must **not** set `Content-Type: application/json`; the browser needs to set its own `multipart/form-data; boundary=...` header for `FormData` bodies.
- Each asset row shows filename, a `formatBytes()`-formatted size, uploader name, a **Download** link, and a **Delete** button.
- **Download** is a plain `<a href="{API_BASE_URL}/meetings/:id/assets/:assetId/download">`, not a fetch — same reasoning as the OAuth connect links on the list page: a same-site top-level navigation carries the session cookie automatically (`SameSite=Lax`), and letting the browser handle the download natively means no manual blob/`URL.createObjectURL` plumbing.
- **Delete** calls `DELETE /meetings/:id/assets/:assetId`, then refetches.
- No frontend distinction between a manually-uploaded asset and one pulled in automatically from a Zoom cloud recording — both are just rows in `meeting.assets` and render identically. "Sync now" on the Meetings list page populates these the same way clicking "+ Upload recording" here does (see backend.md's "Zoom cloud recording sync").

**Tasks section:**
- A small inline form (title input, assignee `<select>` defaulting to "Unassigned", `<input type="date">`) posts to `POST /meetings/:id/tasks`, clears itself, and refetches.
- Each task row is a checkbox (`checked={t.done}`, toggling calls `PATCH /meetings/:id/tasks/:taskId`) plus title (struck through via `line-through` when done), assignee name, and due date. No delete button — see "Known gaps" below.
- No optimistic updates — every toggle/add round-trips through a full refetch, consistent with how Projects/Meetings list pages already treat the server as the source of truth rather than merging partial responses into local state.
- **Only the assignee can check the box** — direct request, matching `meetings/backend.md`'s completion-permission rule. `canToggleTask()` disables the checkbox (`opacity-40`, native `title` tooltip) whenever the task isn't assigned to the logged-in user (`useAuth().user`). **Unassigned tasks are also disabled for everyone** — revised after a bug report where a task's title named specific people but its `assignee` field was never set, so the original "unassigned = anyone can toggle" carve-out let an unrelated user check it off. The tooltip now branches: `"Only <Name> can mark this done"` when a (different) assignee exists, `"Assign this task before it can be marked done"` when there's none. Checking a permitted task opens the `ReasonModal` asking "What did you do to complete this task?" (originally a native `window.prompt`, later replaced — see "Centered reason modal" below) — canceling aborts without calling the API; a real answer sends `{ done: true, note }`. Unchecking (reopening) sends `{ done: false }` with no prompt. Any rejected request (e.g. a stale UI letting a now-invalid toggle through) surfaces via `window.alert(err.message)` rather than failing silently — defense in depth behind the disabled state, not the primary guard. Once done, the row shows the stored note underneath the meta line: `✓ <completionNote>`, italic and muted.
- **"+ Invite teammate"** link sits below the assignee `<select>`. Added after noticing the assignee dropdown only ever lists real org users (`GET /users`), while a synced meeting's real participants (Zoom/Google invitees) often aren't registered — no way to assign a task to someone who was actually on the call. Opens a small two-field modal (name, email) that `POST`s to `/users/invite` (see `landing-login/backend.md` for the endpoint). On success the modal swaps to a confirmation view showing the generated temporary password (no email-sending exists in this demo, so it's shown once for the inviter to copy/share manually) with a "Done" button that closes the modal *and* refetches the org users list — the newly invited person shows up in the assignee dropdown immediately, no page reload needed.

**Participants section:**
- Renders above the Assets/Tasks grid, only when `meeting.participants.length > 0` — a row of pill chips, each with a small avatar (initials, or the first letter of the name uppercased when `initials` is `null` — true for email-only external invitees) and the person's name. Hovering a chip shows their email in a native `title` tooltip when one exists.
- `ParticipantDescriptor` (`app/src/lib/api.ts`) is `{ userId, name, initials, email }` — `userId`/`initials` are `null` for participants who aren't an org member (an external Zoom/Google invitee whose email didn't match anyone in `users`). The frontend doesn't need to care which case it is; it just falls back to the name/email it's given.

## Cross-meeting Tasks page (TasksPage.tsx)
Fetches `GET /tasks?filter=` — `all|open|done` filter chips mirror the same visual pattern as `KnowledgePage.tsx`'s type filters (`Label · N`, counts always reflect org-wide totals so every chip shows its own number regardless of which is selected — see backend.md). The `filters` array carries a `key` (the wire value) separately from a `countKey` (camelCase, to read `data.counts.open` etc.). Each task row is visually identical to `MeetingDetailPage.tsx`'s task rows (checkbox, strikethrough-on-done title, assignee, due date, Delete button) with one addition: the meeting title renders as a `<Link to={\`/app/meetings/${t.meetingId}\`}>` so clicking it jumps straight to that meeting's detail page.

**"Assigned to me" and "Due this week" chips were removed**, direct request, once the `Assignee` dropdown and `Due date` range picker (below) made them redundant with a more general control already on the page — asked to explain the tradeoff first, since it wasn't a perfectly even trade: picking your own name in `Assignee` reproduces "Assigned to me" exactly, but `Due date`'s presets are all backward-looking ("Last 7 days," not "next 7 days"), so getting the same result as the old "Due this week" chip now takes a manual two-click range selection instead of one click. Confirmed and removed anyway. `overdue` was kept as a chip — "overdue" is `due_date < today`, a different date every day, which a fixed-range picker has no way to express as a reusable preset the way a live server-computed chip can.

**Every row always shows a date** (direct request — previously a task with no resolved due date showed nothing at all): `Due <date>` when `dueDate` is set, styled red-and-bold via `isOverdue()` when that date has passed and the task isn't done; otherwise a fallback so a task is never date-less even when auto-extraction couldn't resolve a due date from its source text. `formatDate()` handles every date field with one helper — all of them parse fine as a date-only display without needing the full-ISO-string treatment other timestamp bugs in this codebase required (that bug class was about *time*-of-day precision — `toLocaleDateString()` here only ever needs the date part).

**The fallback is the meeting's date, not the task's `createdAt`** — fixed after a direct report that the fallback showed "Added Aug 6" (the day the auto-extraction backfill script happened to run) on tasks whose real underlying meeting was from late June, which read as flatly wrong. `createdAt` is *when this row was inserted into `meeting_tasks`* — for anything auto-extracted, that's sync/backfill time, not any date a person would recognize. `tasks.ts`'s `GET /` now joins in `m.scheduled_at AS meeting_scheduled_at` and serializes it as `meetingScheduledAt`; the frontend fallback became `Meeting <date>` using that field instead. `createdAt` is still returned by the API (still drives the page's sort order, see below) but is no longer rendered anywhere on this page.

**"Overdue" and "Due this week" chips both removed**, direct requests, once the `Assignee` dropdown and `Due date` range picker (below) covered the same ground with more general controls. "Overdue" was the one chip flagged as *not* having a true replacement — it's `due_date < today`, a moving target no fixed date-range preset can express — but removed on request anyway. The row-level red-highlighting of overdue due dates (`isOverdue()`, used in the row rendering below) is a separate, untouched feature — an overdue task's due date still shows in red-bold on its row, it's just no longer filterable as its own chip.

**Assignee-only completion + required reason**, same feature and same mechanics as `MeetingDetailPage.tsx` (see above — `canToggle()`, the unassigned-tasks-are-locked-too fix, the `window.prompt` note capture, `window.alert` on rejection, the `✓ <completionNote>` line under a done task). The logic is duplicated between the two pages rather than extracted into a shared hook — small enough (one gating function, one prompt call) that a shared abstraction wasn't obviously worth it yet; worth revisiting if a third task-list surface shows up.

**Inline assignee reassignment**, direct follow-up to the lock: once unassigned tasks became uncheckable for everyone, there was no way to actually *unlock* one from this page — you'd have to know to go find it on `MeetingDetailPage.tsx` instead. Replaced the plain assignee text (`{t.assignee ? t.assignee.name : 'Unassigned'}`) with a `<select>` right in the meta line, styled to blend in (`border-0 bg-transparent`, underline on hover) rather than look like a form control, red text specifically when unassigned so a locked task's fix is visually obvious in the row itself. `handleAssign()` PATCHes `{ assigneeId: value || null }` to the same `PATCH /meetings/:id/tasks/:taskId` endpoint everything else on this page already uses, then refetches — picking a name unlocks that person's checkbox immediately on the next render, no navigation required. Verified live (via `select` on the dropdown, not raw DOM `.value` assignment — the latter doesn't reliably fire React's `onChange` on a controlled `<select>`): assigning the previously-locked "Aurosmita & Lopita" Docker task to a user flips its checkbox from `disabled: true` to `disabled: false`; reassigning back to "Unassigned" locks it again.

**Reason prompt + confirmation + expandable journey**, direct follow-up describing the exact flow wanted: after picking a name, a field should pop up for a reason, then save, then a confirmation popup, and "this journey" should be viewable somewhere. Asked where — expand the row itself (see backend.md for the `task_activity` table and `GET .../activity` endpoint this reads from).

- `handleAssign()` now branches on whether the new value is a real change and a real person: picking the *same* assignee already on the task is a no-op (`return` immediately, no request); clearing to "Unassigned" fires the `PATCH` straight away with no prompt, since there's nothing to justify; picking a *different* person opens a reason prompt first (originally `window.prompt`, see "Centered reason modal" below for why that changed). Canceling calls `fetchTasks()` (no mutation) rather than just `return`ing — needed because a `<select>`'s native value changes on click *before* `onChange` fires, and since nothing here calls `setState` on cancel, React never gets a render to snap the controlled `<select>` back to the real (unchanged) value on its own. Verified live: canceling on a disposable test task left the visible dropdown on the just-picked name until this fix, `assignedAfterCancel` confirmed back to the real assignee after.
- A real reason submits `{ assigneeId, reason }`, and on success pops `window.alert(\`Task assigned to <Name>.\`)` — the confirmation the request asked for.
- **Marking done gained the same confirmation** ("the done action can be taken as of this strategy") — `handleToggle()` now pops `window.alert('Task marked done.')` right after a successful `done: true` PATCH. It already collected a reason (the completion-note prompt); this only added the success popup. Reopening (`done: false`) still has neither prompt nor confirmation — not part of this request.
- **The journey itself**: a `History ▾/▴` toggle button on the right of each row's top line. Expanding it (`expanded: Set<string>`, `activity: Record<taskId, TaskActivityEntry[]>`) lazily fetches `GET /meetings/:id/tasks/:taskId/activity` once and caches it; toggling closed just hides the cached list rather than re-fetching. If the row's own assign/done action just changed something and the panel happens to already be open, the handlers re-fetch that task's activity immediately so the log doesn't show stale entries until a manual re-toggle. Each entry renders as `"<Actor> assigned this to <Assignee>" / "marked this done" / "reopened this"` (a small `activityLabel` lookup keyed by `action`) plus a `formatDateTime()`'d timestamp and, when present, the reason in a quoted italic line underneath. `formatDateTime()` needs the same `'YYYY-MM-DD HH:MM:SS'` → ISO treatment as other SQLite timestamps in this codebase (append `Z` after swapping the space for `T`, so it parses as the UTC instant it is rather than local time).
- Applied identically to `MeetingDetailPage.tsx`'s per-meeting task list (`toggleTaskHistory()`/`loadTaskActivity()`, same `activityLabel`/`formatDateTime`) for the "done" confirmation and the journey panel — that page doesn't have inline reassignment (no `<select>` there, just the plain assignee name), so only the completion side of this feature applies there; the journey panel still shows any `assigned` entries logged elsewhere (e.g. from `TasksPage.tsx`), since both pages read the same `task_activity` log for the same task.

Verified end-to-end via curl (reassigning without a `reason` → 400; with one → 204 and the activity log shows it; marking done adds a second entry) and live in the browser: expanding History on the Docker task after both actions rendered `"Ambika assigned this to Ambika · 6 Aug, 19:35"` with the reason quoted underneath, followed by `"Ambika marked this done · 6 Aug, 19:36"` with the completion note quoted underneath.

### Centered reason modal (as built)
Direct report, with a screenshot: the `window.prompt()` used for both the assignment reason and the completion note rendered docked to the **top** of the browser chrome, not centered — a native browser dialog, so no CSS in the page can reposition it. The only fix is not using a native dialog for this.

Added `app/src/components/ReasonModal.tsx` — a small centered modal (overlay + `fixed left-1/2 top-1/2 ... -translate-x-1/2 -translate-y-1/2` box) that mirrors the existing "Invite teammate" modal's exact styling (`MeetingDetailPage.tsx`, built earlier — same overlay opacity, box shadow, corner radius, button treatment) so the two dialogs in this app look like one system rather than two. Props: `title`, optional `description`, `confirmLabel`, `onSubmit(reason)`, `onCancel()` — a `<textarea>` instead of `window.prompt`'s single-line field, since a multi-line box gives more room for an actual explanation.

Both `TasksPage.tsx` and `MeetingDetailPage.tsx` replaced their `window.prompt()` calls (assignment reason, completion note) with a `pendingReason: PendingReason | null` state slot holding `{ title, confirmLabel, onSubmit, onCancel }`, set by `handleAssign()`/`handleToggle()` instead of calling `window.prompt()` directly, and rendered once at the bottom of the page. This also fixed a **second**, previously-unnoticed bug in the same family as the `<select>`-revert issue above: a checkbox's native `checked` flips the instant it's clicked, before `onChange` runs, so canceling the completion-note prompt without forcing a re-render left the checkbox visually checked even though the task was never actually marked done. Both pages' cancel handlers now call `fetchTasks()`/`fetchMeeting()` to force the reconciliation, same fix as the assignee `<select>`.

Verified live: reassigning a real task through the new modal (screenshot confirmed it rendered dead-center in the viewport, not top-docked) and submitting a reason correctly PATCHed the assignee and reason through to the API and the activity log; canceling correctly closed the modal and left the assignee unchanged.

**Follow-up: the two success confirmations had the same top-docked problem.** `window.alert('Task assigned to <Name>.')` and `window.alert('Task marked done.')` are also native dialogs — same fix needed. Added `app/src/components/ConfirmationToast.tsx`: centered (`fixed left-1/2 top-1/2 ... -translate-x-1/2 -translate-y-1/2`), auto-dismisses after 2.2s via a `setTimeout` cleaned up on unmount, **no dimming overlay** — unlike `ReasonModal`, this is a passive confirmation rather than a decision, so the task list underneath stays interactive while it's showing rather than getting blocked. Both pages replaced those two `window.alert()` calls with `setConfirmation(message)` (a plain `string | null` state slot) and render `<ConfirmationToast message={confirmation} onDone={() => setConfirmation(null)} />` at the bottom of the page. Error alerts (`"Could not update the task."` etc.) were left as native `window.alert()` — not part of this request, and arguably fine to stay blocking/attention-grabbing for a failure in a way a passive success toast shouldn't be.

Verified live: marked a disposable test task done through the real UI flow (checkbox → `ReasonModal` note → submit) and screenshotted the resulting toast rendering dead-center over the task list, not top-docked. Doing this surfaced a real, unrelated bug: deleting a task that has any `task_activity` rows (which, after the journey feature, is any task that's ever been reassigned-with-reason or marked done/reopened) failed with a SQLite `FOREIGN KEY constraint` error — the `DELETE /:id/tasks/:taskId` handler was never updated to also delete the task's `task_activity` rows first. Fixed in `meetings.ts` by deleting `task_activity WHERE task_id = ?` immediately before the `meeting_tasks` delete. Since the Delete button itself is UI-removed (see above), this only affected direct API callers — but that includes this doc's own "create a disposable test task, delete it via curl afterward" verification pattern used throughout this session, which is exactly how it was caught.

**Assignee + date range filters**: `Assignee: <select>`, `Meeting date: …`, `Due date: …`, all additive to whatever chip filter is active — direct request for "a real user filter and a real date range filter." The assignee `<select>` is populated from `GET /api/users` (same endpoint `MeetingDetailPage.tsx`'s task-assignee dropdown already uses — reused as-is, no new endpoint) and lists every registered user including the auto-created placeholder accounts from `meetings/backend.md`'s auto-task-extraction feature, same tradeoff already accepted there. Asked whether the date range should filter by due date or meeting date; the answer was **both, as independent ranges** rather than picking one — `meetingRange`/`dueRange` map straight onto `tasks.ts`'s `meetingFrom`/`meetingTo`/`dueFrom`/`dueTo` query params. A **Clear** button (only rendered once assignee or either range is set) resets all three in one click. Every field is a `useEffect` dependency, so any change refetches immediately — no separate "Apply." Verified live: selecting a specific assignee correctly narrowed 322 tasks to that person's 19 and updated every chip count to match; a June meeting-date range independently narrowed to 203; Clear correctly reset back to all 322.

**"Unassigned" added to the Assignee filter**, direct follow-up — the dropdown only ever listed real users, so there was no way to filter down to the ~71 tasks with no assignee at all (a real number worth seeing at a glance, given completion is now locked for every one of them — see `meetings/backend.md`'s completion-permission section). A plain `<option value="unassigned">` was added right after "Everyone"; `unassigned` can never collide with a real assignee id since those are UUIDs. `tasks.ts`'s `applyExtraFilters()` special-cases it: `assigneeId === 'unassigned'` filters `t.assignee_id IS NULL` instead of binding it as a literal id to compare against. Verified via curl (`?assigneeId=unassigned` → 71 items, every one confirmed `assignee: null`) and live: selecting "Unassigned" narrowed the page to those 71 rows, each showing the red "Unassigned" text already used to flag a locked task.

**Merged onto one row**, direct follow-up. Originally the three chips and the assignee/date controls were two separate blocks — chips in a plain flex row, the other three wrapped in their own bordered card underneath, each with its own `mb-4.5`. Direct request to put everything on a single line: dropped the second block's card wrapper (`rounded-2xl border bg-card p-3.5`) and merged all of it into the chips' own `flex flex-wrap items-center gap-2` row, with `ml-2` on the `Assignee` label as the only seam between "chip group" and "filter controls." `flex-wrap` still lets it drop to a second line on a narrow viewport rather than overflowing, but at the page's normal width everything — chips, Assignee, Meeting date, Due date, Clear — now sits on one line.

**Date range inputs are `DateRangePicker` (`src/components/DateRangePicker.tsx`)**, not native `<input type="date">` pairs — originally built that way, then replaced per direct request to match a reference screenshot of a calendar-dropdown range picker. Both `meetingRange` and `dueRange` are `DateRangeValue | null` state fed straight into two `<DateRangePicker>` instances; see `knowledge-base/frontend.md` for the component itself (built there first, this page is its second and third use) — including why its popover positioning needed a real post-render measurement rather than a fixed left/right alignment: with three filters (Assignee, Meeting date, Due date) packed into one row, the rightmost ("Due date") trigger didn't have enough clear space on *either* side for the ~730px popover at a standard 1280px viewport, which a simple "pick whichever side looks less bad" rule couldn't handle correctly. Verified live at 1280px: all three triggers open fully on-screen, no clipped presets or calendar columns.

Mutations (`handleToggle`, `handleDelete`) call the *existing* per-meeting endpoints directly (`PATCH`/`DELETE /meetings/:meetingId/tasks/:taskId`) using the `meetingId` included on every task from `GET /tasks` — no new mutation endpoints were added, this page is purely a different read/entry surface over the same task data `MeetingDetailPage.tsx` already manages. No "add task" form here (unlike the per-meeting page) — creating a task without picking which meeting it belongs to doesn't make sense, so that stays a meeting-scoped action.

Verified live: toggling a task's checkbox here updates its strikethrough and moves the `Open`/`Done` chip counts immediately; deleting removes it from the list — both confirmed against the actual API response, not just the optimistic UI state.

**Sort order**: originally `done ASC, due_date IS NULL, due_date ASC, created_at DESC` (soonest-due first) — changed to `done ASC, created_at DESC` (most recently created first) per direct request once the auto-task-extraction feature (see backend.md) started populating this page with a large batch of tasks at once; due-date-first ordering buried the newest additions wherever their due date happened to fall instead of surfacing them at the top. Due date is still shown on each row, it's just no longer the sort key. Verified via curl (newest `createdAt` first, oldest last) and live in the browser.

## Known gaps
- "Sort: Most recent ⌄" is still decorative (list is always ordered `scheduled_at DESC` server-side, so it happens to already look "sorted by most recent" — just not user-controllable). See `projects/frontend.md` for how the equivalent control was made real on the Projects page — same fix would apply here.
- Participant chips only appear on the detail page, not the list page's compact rows — adding them there would need a smaller avatar-stack treatment (like Projects' owner avatar) to fit the row height, not yet built.
- No "Needs review" write-back — marking a meeting reviewed isn't possible from the UI (the chip only filters by existing `sync_status`, it doesn't change it).
- No loading/spinner state on individual Connect/Disconnect buttons — only "Sync now" shows a busy state ("Syncing…").
- No upload progress bar — a large recording just shows "Uploading…" on the label with no percentage, since the upload uses `fetch` rather than `XMLHttpRequest` (which is what you'd need for real progress events).
- No audio/video player inline for recordings — assets are download-only, not previewable in the browser.
- No edit UI for an existing task's title/due date — the done checkbox and the inline assignee `<select>` (see below) are wired; title/due date would need opening some kind of edit affordance that doesn't exist yet.
- **Delete removed from both task-list surfaces**, direct request ("let's remove the delete option for the time being") after adding a confirm prompt and an assignee-only restriction to it. Both `handleDelete()`/`canDelete()` (`TasksPage.tsx`) and `handleDeleteTask()`/`canDeleteTask()` (`MeetingDetailPage.tsx`) were deleted along with the button — no dead code left disabled-but-hidden. `DELETE /meetings/:id/tasks/:taskId` still exists server-side with its assignee-only check intact (see backend.md); only the UI entry point is gone, so it's a quick re-add if the feature comes back.
- `TasksPage.tsx` has no user-facing sort control (order is fixed server-side — most recent first, see above) and no "add task" form (by design — see above) and no pagination (not fine at demo scale anymore now that auto-extraction can add hundreds of tasks at once — see backend.md's gaps).
- The "+ New meeting" participants checkbox list has no search/filter — fine at this org's real scale (12 members), would need one before this stays usable with a larger team.
- No way to edit a meeting's participant list after creation — `participantIds` is create-only, matching the rest of `POST /meetings`'s fields (no `PATCH /meetings/:id` exists at all yet).
