# Projects (All Projects) — Frontend

## Route
`/app/projects` → `src/pages/ProjectsPage.tsx`, inside `AppLayout`. Reached from the dashboard's "See all →" link, the top tab bar, or directly.

## Component structure
Single-file page, no extraction yet.

- `filters` / `statusOptions` — filter chips and the edit/create modal's status `<select>` share the same three statuses but are separate arrays (chips need an "All" option with counts, the form doesn't).
- `useState<filter>` — active filter key, refetches from the server on change (see Data fetching).
- `users` — org member list (`{ id, name, initials }[]`), fetched once on mount from `GET /api/users`, populates the "Owner" `<select>` in the modal.
- `timeAgo(iso)` — local helper, formats an ISO timestamp as "Updated Xh ago" / "Updated Xd ago".

## Data fetching (real, server-filtered — no more client-side array filtering)
```ts
useEffect(() => {
  setData(null)
  api.get<ProjectsResponse>(`/projects?status=${filter}`).then(setData).catch(...)
}, [filter])
```
`ProjectsResponse` = `{ items: ProjectItem[], counts: Record<string, number> }` — both the list AND the chip counts (`All · 8`, `On track · 4`, ...) now come from the server (`GET /api/projects?status=`, see backend.md), computed via a separate `GROUP BY status` query so counts stay correct even when the visible list is filtered. `ProjectItem` now includes `description: string` and `owner: { id, name, initials }` (previously `owner` had no `id`, which made pre-filling an edit form impossible).

## "+ New project" and card-click-to-edit — one shared right-side drawer
Both flows use a single panel (`modalMode: 'create' | 'edit' | null`) and a single form-state object (`ProjectFormState = { name, description, status, ownerId, gitUrl, deploymentUrl, username, password }`), rather than two separate panels with duplicated markup:

- **Create**: "+ New project" button (top-right of the heading, moved here earlier from the shared top bar) calls `openCreate()`, which resets the form to `EMPTY_FORM` and opens the drawer in `'create'` mode.
- **View/Edit**: every project card is now a `<button>` (the whole card is clickable, not just some sub-element) that calls `openEdit(p)`, pre-filling the form from that project's current `name`/`description`/`status`/`owner.id`. Despite the function's name (kept as-is rather than renamed, to keep the diff smaller), whether the drawer actually behaves as *editable* now depends on ownership — see "View-only for non-owners" below.
- Submit (`handleSubmit`) branches on `modalMode`: `create` → `POST /projects`, `edit` → `PATCH /projects/:id`. Both paths close the drawer and call `fetchProjects()` afterward rather than trying to merge the partial API response into local state — same reasoning as before (the server is the source of truth for owner name/initials/counts/timestamps, which the mutation endpoints don't return in full).

### Right-side drawer, not a centered modal (as built)
Direct request: "the window should be visible from the right drawer." Converted from a centered `fixed left-1/2 top-1/2 ... -translate-x-1/2 -translate-y-1/2` box to a full-height `fixed right-0 top-0` panel, `w-[480px] max-w-[92vw]` — same overlay + slide-in-from-the-right convention `ChatDrawer.tsx` already established for "Ask The Record," reused rather than inventing a second panel pattern.

**Always mounted, not conditionally rendered.** The old modal only existed in the DOM while `modalMode` was truthy, so it could only ever appear/disappear instantly — no exit animation, since there's nothing to animate the *removal* of an element that's already gone. The drawer is now always rendered; `modalMode` drives `translate-x-0` (open) vs `translate-x-full` (closed, fully off-screen past the viewport's right edge) via a CSS `transition-transform`, so both the slide-in *and* the slide-out play. The overlay (`bg-ink/25`) follows the same always-mounted pattern, toggling `opacity-100`/`pointer-events-none opacity-0` instead of mounting/unmounting.

**`displayMode` — a second state that lags `modalMode` on purpose.** With the panel always mounted, `modalMode` going `null` on close is no longer just "unmount it" — the panel is still visible and animating out for ~250ms. Anything in the panel's content that branches on `modalMode === 'create'` (the header title/subtitle, the "Attach documents" section, the submit button's label) would flip to its `'edit'`-branch fallback the instant `modalMode` goes `null`, which is now visible as a flicker partway through the close animation instead of invisible. `displayMode` mirrors `modalMode` but only ever updates on a non-null value (`useEffect(() => { if (modalMode) setDisplayMode(modalMode) }, [modalMode])`) — so it keeps showing whatever was last open throughout the whole close transition, and only changes again the next time the drawer actually opens. `modalMode` itself is untouched for anything that isn't purely cosmetic (`handleSubmit`'s branch, `closeModal`'s reset) — a closed, off-screen panel can't be submitted by a real user regardless, so there was no correctness reason to touch that logic.

Content now scrolls independently of the header: a fixed `border-b` header (title/subtitle) sits outside a `flex-1 overflow-y-auto` region wrapping the `<form>`, so a tall form (all 8+ fields plus a growing "Attach documents" file list) scrolls within the panel rather than the header disappearing off the top of a viewport-height overflow.

Verified live: opened "New project," confirmed via `getBoundingClientRect()` that the drawer settles at `left: 960, right: 1440` in a 1440px viewport — flush against the right edge, exactly `480px` wide, not a coincidence of the screenshot. Opened the edit drawer via a real project card click and confirmed the title/fields/button label all correctly showed "Edit project" / pre-filled values / "Save changes" (no "Attach documents" section, matching the create-only scoping). Clicked Cancel and confirmed via a fresh `getBoundingClientRect()` that the panel moved to `left: 1440` — fully past the viewport's right edge, closed. Also directly verified (via `closest('button')` in the live DOM, not just visual inspection) that the panel is a true sibling of the projects grid, not nested inside a project card's `<button>` — the accessibility-snapshot tool used for testing has a cosmetic indentation quirk around this always-mounted overlay that looks like DOM nesting but isn't; the real DOM structure is correct.

Form fields: Project name (text input), Description (3-row `<textarea>`), **Attach documents (optional)** — create mode only, see below — Status (`<select>`, defaults `on_track`), Owner (`<select>`, defaults to "Me" — an empty string value that the backend resolves to the requesting user), Git URL (text input), Deployment URL (text input), Username (text input), Password (**`type="text"`, not `type="password"`** — see below). Save/Create button disabled while `saving` or the name is empty. Inline error box (`formError`) shows API failures (e.g. an invalid `ownerId`) using the same red-box pattern as the login page.

### View-only for non-owners (as built)
Direct request: "each project on the dashboard needs to be clickable so that each one view the details but it can't be editable except the owner." The clickable-from-the-Dashboard half of this now lives entirely on the Dashboard itself — see `dashboard/frontend.md`'s "Read-only project panel" section — not here; this page only covers the ownership gate on its own card clicks.

**Tried, then undone: a Dashboard → Projects deep link.** The first version made the Dashboard's cards `<Link to={\`/app/projects?open=\${p.id}\`}>`, and had `ProjectsPage.tsx` read the `open` query param on mount to fetch and open that project's drawer automatically. Undone on direct follow-up — "why it is redirecting to the project project. It needs to on the same page" — since navigating away wasn't what was wanted; the Dashboard needed its own self-contained view, not a hop to this page. The query-param handling (`useSearchParams`, the `open`-reading `useEffect`) was removed outright rather than left dead. Noted here so a future "why isn't there a deep-link param" question isn't asked from stale memory of the tried-then-reverted version.

**`canEdit` gates the whole drawer, not just the submit call** — this part stayed, since clicking a card *on this page* still needs to behave correctly regardless of ownership, independent of how the Dashboard handles its own clicks. A new `editingOwnerId` state, set in `openEdit()` alongside the existing `editingId`, captures who owns the project the drawer currently has open — independent of `form.ownerId`, since that field is itself one of the things being gated (it can't decide its own gate). `canEdit = displayMode === 'create' || editingOwnerId === user?.id` (always editable while creating — there's no owner yet to defer to). When `!canEdit`:
- Header reads "View project" / "Only the project owner can make changes here." instead of "Edit project" / "Update any of the details below."
- Every field (name, description, status, owner, Git URL, deployment URL, username, password) gets `disabled` — same visual treatment (`disabled:cursor-not-allowed disabled:opacity-70`) across all of them, not a mix of hidden/shown fields.
- The submit button ("Save changes") doesn't render at all — not just disabled, genuinely absent — and "Cancel" relabels to "Close," since there's nothing to cancel out of.
- `handleSubmit` itself also short-circuits on `!canEdit` as a second layer, even though the button being gone and the fields being disabled already prevent a normal user from reaching it — defense in depth, not load-bearing on its own (the real enforcement is server-side, see `projects/backend.md`).

Verified live: reassigned the real project's owner to a different user directly in the DB, clicked its card on `/app/projects`, and confirmed the drawer opened as "View project" with every field visibly disabled, the Owner `<select>` correctly showing the *new* owner selected, and only a "Close" button — no way to submit. Reassigned ownership back to the real owner, repeated the same click, and confirmed it now opened as "Edit project" with all fields editable and "Save changes" present. Both checked via the accessibility tree (`[disabled]` markers) as well as a screenshot, not just visual inspection.

### Attach documents on create (as built)
Direct follow-up chain: "why is this showing 0 doc and 0 meetings" → "where's the upload option" → confirmed no automatic or manual path existed at all → "while creating the project details, there should be a field to upload the doc if any" → "there is no option to add multiple doc." A native `<input type="file" multiple>` (styled via Tailwind's `file:` variant classes, not a custom dropzone) renders **only when `modalMode === 'create'`** — a new `docFiles: File[]` state, reset to `[]` in `openCreate()` and after a successful submit, has no equivalent field in `ProjectFormState` since it's not one of the plain-text project fields.

**Accumulating selection, not replace-on-pick.** The input's `onChange` appends newly picked files to `docFiles` (`setDocFiles((prev) => [...prev, ...picked])`) rather than replacing it, and resets the input's own value afterward (`e.target.value = ''`) — a native multi-select `<input>` only ever reports the files picked in that one dialog, so without accumulating, opening "Choose Files" a second time would silently drop whatever was selected the first time. Selected files render as a list below the input, each with its own "×" remove button (`setDocFiles((prev) => prev.filter((_, idx) => idx !== i))`) — so a person can multi-select several files at once *and* remove one they change their mind about before submitting, without needing to redo the whole selection.

`handleSubmit`'s create branch changed from `api.post('/projects', {...})` (JSON) to building a `FormData` and calling `api.upload('/projects', formData)` — every field appended as a string, each file in `docFiles` appended under the repeated `files` key (`docFiles.forEach((f) => formData.append('files', f))` — see `projects/backend.md` for why the backend needed to switch to multipart, and to `.array()` instead of `.single()`, to receive them). The edit branch is untouched — still `api.patch` with a plain JSON body, since there's no file field on edit.

Verified live: opened "New project," filled the name, selected 3 files at once through the actual native file-picker (not simulated via JS), confirmed all 3 listed with individual remove buttons, removed one via its "×," confirmed only the other 2 remained in the list, then submitted. Confirmed the new project's card showed "2 docs" — matching exactly what was left after the removal, proving the remove button's effect actually reached the request rather than just updating the visible list. Earlier, confirmed a single-file case too: card showed "1 docs" (the original symptom that started this whole thread) and the file appeared correctly in the Knowledge Base — see `knowledge-base/frontend.md` for that side of the verification.

### Environment/deployment fields (Git URL, Deployment URL, Username, Password)
Added per direct request, to hold each project's linked repo/environment access: where the code lives, where it's deployed, and the login for that environment. Two decisions were made explicitly by the user, not inferred:
- **Modal-only, never on the card.** These four fields only ever render inside the create/edit modal — the card grid (see Card content below) shows none of them. Confirmed directly when asked where they should surface.
- **Password is plain, unmasked text — both in the UI and in storage.** The input is `type="text"`, not `type="password"`, so the value is always visible while editing, and the backend stores it as-is with no hashing/encryption (see `projects/backend.md`). This was the user's explicit choice ("Keep as normal text") after being asked how to handle it — not a default or an oversight.

## Card content
Project cards now show the description (`line-clamp-2`, only rendered if non-empty) between the name/status row and the owner row — this was the actual point of the feature: a project entry that's more than just a name. Git URL, Deployment URL, Username, and Password are deliberately excluded from the card — see above.

**Meeting count removed from the card**, direct request — after confirming *why* a project showed "0 meetings" (no meeting has `project_id` set to it yet; see `meetings/frontend.md`'s "+ New meeting" form and `projects/backend.md`'s `meetingCount` query — the mechanism to link one exists and already works, unlike the doc-attach gap this same conversation surfaced), the user asked for the number itself to stop showing on the card. Removed outright, not hidden behind a conditional — the card now shows only `docCount` ("N docs") in that row, no "· N meetings" alongside it. `p.meetingCount` still comes back from `GET /api/projects` (untouched on the backend — this was a display-only removal) and is simply unused by this render.

**Owner and docs count merged onto one line**, direct follow-up: "can we keep them in a single line and the member name on the right side of doc count?" — the owner row (avatar + name) and the docs row used to be two separate `mb-4`/`mb-3.5` blocks, stacked. Now one `flex items-center justify-between` row: `docCount` "N docs" on the left (unchanged), the owner avatar + name on the right (unchanged internally, just moved into the same row instead of its own). This is a different change from the earlier "name next to docs count" one (see above) — that was about the *project name*, tried and undone; this is about the *owner's* name, which stuck.

**Name-onto-docs-line change, tried then undone**: a direct follow-up ("Name and doc count should be visible on the same line. The name should be visible at the right side of the doc count") moved the name off the top heading down onto the docs row (status pill left alone at top, "N docs … Name" sharing the line below), confirmed via a side-by-side preview comparison before building it. Immediately undone on request ("undo the last previous change") — back to the original: name + status pill together in the top heading row, `docCount` alone on its own row beneath the owner row. Noted here so a future "why does the name sit next to docs count" question isn't asked from stale memory of the tried-then-reverted version.

## Sort
Real native `<select>` next to the filter chips (`sortOptions`: Recently updated, Name (A-Z), Status), replacing what used to be a decorative `Sort: Recently updated ⌄` label with no control behind it. Sorting is done client-side over the already-fetched `data.items` (a `sortedItems` derivation, recomputed on render) rather than a new server param — reasonable at this scale since the backend already returns the full filtered set with no pagination. "Recently updated" re-sorts by `updatedAt` descending (matching the server's default order); "Status" groups by a fixed weight (`attention` → `blocked` → `on_track`) so the projects needing attention surface first.

## Known gaps
- No pagination (fine for the seeded ~9-12 projects, not fine at real scale — the backend endpoint doesn't support `page`/`limit` params yet either).
- No dedicated project detail page/route — clicking a card opens the drawer (view-only or edit, depending on ownership) as page-local state, not a full detail view at its own shareable URL. The Dashboard has its own separate, independent read-only panel for the same reason — see `dashboard/frontend.md` — rather than linking here.
- No Escape-key-to-close and no focus trap on the drawer — same gap `ChatDrawer.tsx` (the pattern this was modeled on) already has, not something newly introduced here.
- No delete action anywhere in the UI, despite nothing blocking it at the backend level beyond a missing `DELETE` endpoint.
- Owner dropdown lists every org member with no search/filter — fine for a 5-person seeded org, would need a combobox at real team size.
- The document-attach field only exists on create, not edit — there's no way to attach a document to a project after the fact from this page (the Knowledge Base's own manual-add endpoint has no frontend caller either — see `knowledge-base/frontend.md`).
- No per-file size/type validation client-side before upload — a too-large or unexpected file only fails once the request reaches the backend's 20MB-per-file multer limit, surfacing as a generic error rather than a specific "that file's too big" message at selection time.
- Capped at 10 files (matches the backend's `MAX_PROJECT_DOC_FILES`), with no client-side warning if more are selected — see `projects/backend.md`'s note on the resulting unhandled 500 if that cap is ever exceeded.
