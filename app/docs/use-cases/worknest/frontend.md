# WorkNest — Frontend

## Route
`/app/worknest` → `src/pages/WorkNestPage.tsx`. Entry point is a new **WorkNest** item in the account dropdown (`AppLayout.tsx`), sitting between "`{org_name}` Holidays" and "Log out" — same dropdown, same pattern established when Holidays moved there (see `landing-login/frontend.md`).

## Component structure
One page, one section — originally two tabs (`tab: 'leave' | 'payslips'`), until Payslips was removed (see below). Now `WorkNestPage.tsx` renders the leave content directly, no tab state, no tab switcher UI.

### Leave
Two-column **grid** layout — direct follow-up to the initial single-column build — "leave requests and its status needs to be visible on the right hand side section of the page," matching the reference screenshot's right-side "Notifications" panel:

- **Left column**: Leave balance (5-column grid of stat tiles, one per leave type, all on a single row — see history below for why), **Log leave** (self-service, no approval — see "Leave request/approval workflow — removed, then self-service logging added back" below), **Team on leave** (see below), and — admin only — **Team leave balances** (see "Admin balance adjustment" below). Originally had an admin-gated Apply-for-leave + Team requests approval queue instead of Log leave — see that section for the full history.
- **Right rail**: **Leave history** (renamed from "My requests" — same section) — the caller's own `GET /worknest/leave-requests`. Each card shows day count + type as the heading, then dates, reason, and a status pill (`pending` = neutral gray, `approved` = green, `rejected` = red — reusing the exact `bg-green-tint`/`text-green` tokens already used for the "Synced" pill elsewhere in this app), stacked in a single column. `sticky top-7` keeps it in view while the left column scrolls.

**Column widths — a fixed 70/30 split**, `grid-cols-[7fr_3fr]` on the outer container, not flexbox. `fr` tracks split the *available* width after the grid's own `gap-5` is subtracted, so this is a true 70/30 of the usable space — flex-basis percentages on flex children don't have that property (a `gap` between them sits on top of, not inside, the percentage split, so two 70%/30%-basis flex items plus a gap would overflow their container). Verified by measuring the rendered elements directly: 837px / 359px at a 1440px viewport — exactly 70% / 30% of the 1196px they share.

**Three rounds to get here**, all direct follow-ups. Round 1: made the rail `flex-1` and switched its cards to an auto-fill grid to close a right-side blank-space gap — undone on request, reverting the rail to a fixed `w-72`. Round 2 started from a different angle: "make the [balance] section a single line instead of 2" (`grid-cols-3` → `grid-cols-5`) "so that My request will move towards the right." That alone did nothing to the gap — verified by screenshot before touching anything else — because the left column was `flex-1`, which sizes by the flex algorithm (`flex-basis: 0%`) and grows to its `max-w-2xl` cap regardless of how much or little content is inside it; a shorter card just leaves blank space *inside* that column, it can't shrink the column itself. Explained this and asked how to proceed; confirmed wanting the rail to grow, so it became `flex-1` again (keeping the single-column card list this time, no grid-of-cards). Round 3: an explicit "70% / 30%" split was requested — flex's approximate "whatever's left" growth wasn't precise enough, so the whole layout switched from `flex` to `grid grid-cols-[7fr_3fr]`, which is what's live now.

### Team on leave (as built)
Direct follow-up, after the Dashboard's Leave calendar (see `dashboard/frontend.md`) landed its "See all" link on WorkNest's top — which meant Apply-for-leave, not "who's out": "on the leave apply section, there should not be any request. Its only the info to the team that the person is on leave." A card, `id="team-on-leave"`, sits in the left column — visible to **every** org member, no `isAdmin` check, and purely informational: name, avatar initials, leave type, and date range per entry, no buttons, no actions. Backed by `GET /worknest/on-leave` (see `worknest/backend.md`).

The Dashboard's Leave calendar "See all →" now links to `/app/worknest#team-on-leave` instead of a bare `/app/worknest`. A `useEffect` on `WorkNestPage.tsx` (via `useLocation()`'s `hash`) calls `document.querySelector('#team-on-leave')?.scrollIntoView({ behavior: 'smooth', block: 'start' })` when the hash matches — React Router's client-side navigation doesn't get the browser's native anchor-scroll behavior the way a full page load would, so this replaces it by hand. The effect deliberately waits on `balances`/`onLeave` both being loaded before firing, not just on mount: everything above the target card (Leave balance, Apply for leave) starts in a shorter "Loading…" state, and an immediate scroll calculated against that shorter layout lands short once the real content finishes loading and pushes the card further down the page — confirmed by reproducing exactly that bug first (scrolled to a fixed offset that didn't match the card's final position) before adding the loaded-state guard.

### Payslips tab — removed
Direct request: "remove the payslip section only." The tab switcher, the entire `payslips`-branch JSX (My payslips list, admin Generate-a-payslip form), and every payslip-specific piece of frontend state (`payslips`, `orgUsers`, `payslipUserId`/`Period`/`Basic`/`Deductions`, `generating`, `payslipError`) and handler (`fetchPayslips`, `handleGeneratePayslip`) were deleted from `WorkNestPage.tsx` outright — not hidden behind a flag, no dead code left disabled. `Payslip`/`OrgUser` type imports dropped from the page along with everything that used them. Since Payslips was the only other tab, removing it left nothing to switch between — the tab button row and `tab` state came out too, and the page now renders the leave content directly (see "Component structure" above).

**Backend later removed too.** For a while after this, `GET/POST /worknest/payslips` and the `payslips` table stayed exactly as they were (see the "remove the UI, leave the endpoint" pattern already used for the Tasks page's Delete button, `meetings/backend.md`) — reachable directly, just with no UI entry point. A follow-up direct request ("remove the payslip section, I don't need that one") closed that gap for good: the endpoints, the table, and the 3 real payslip rows that had been migrated into Neon are all gone now — see `worknest/backend.md`'s "Payslips — removed" section.

## Leave request/approval workflow — removed, then self-service logging added back
Direct request: "There should be no leave request and approval system within this. But each individual can show their leave history in place of My Requests under worknest." Unlike Payslips (UI removed first, backend followed as a separate later request), this first pass removed UI and backend together in one go — confirmed with the user that the underlying endpoints should be deleted too, not just hidden (see `worknest/backend.md`'s matching section).

Deleted from `WorkNestPage.tsx` in that first pass: the **Apply for leave** `<form>` (leave-type `<select>`, `DateRangePicker`, reason `<textarea>`, submit button) and its state/handler; the **Team requests** admin approval card (pending-requests list, **Approve**/**Reject** buttons) and its state/handler; the `isAdmin` check that gated Team requests; the `leaveTypes` state/fetch (only existed for the Apply form's dropdown); and the `DateRangePicker`/`DateRangeValue` imports. "My requests" was renamed to "Leave history" in the same right-rail slot, same data, just relabeled as a read-only log.

**That left no way to actually add a new entry at all** — surfaced by a direct follow-up question, "How one member will inform the team about the leave where to intimate?", then the actual ask: "without the request/approval, all rest should be there." So a **Log leave** card came back into the left column, between Leave balance and Team on leave — same fields as the old Apply-for-leave form (leave-type `<select>`, `DateRangePicker`, reason `<textarea>`), reusing `leaveTypes` state/fetch and the `DateRangePicker`/`DateRangeValue` imports (all re-added). The differences from the old form are deliberate, not cosmetic:
- **Button says "Log leave," not "Submit request"** — there's no pending state to wait on, submitting is the whole action.
- **No `isAdmin`/Team requests counterpart re-added** — `handleLog()` posts once and the entry is immediately live everywhere (own balance, own history, "Team on leave" for everyone else); there's nothing left for anyone to approve.
- State/handler names reflect this: `logLeaveType`/`logRange`/`logReason`/`logging`/`logError`/`handleLog`, not `apply*`/`handleApply` — a deliberate rename, not a restoration of the deleted names, so nothing in the diff looks like the removal never happened.

**"Leave history"** keeps its name from the first pass (not reverted back to "My requests") — it's still accurate: even though entries can be created again now, the right rail is still a log of what happened, not an actionable queue with pending items to track.

### Insufficient-balance warning shown before submit (as built)
Direct report, from a screenshot: the form let a user pick a 12-day range for Casual Leave while "Leave balance" showed only 8 available, with **Log leave** fully enabled — asked why it was "allowing" that. Traced it to the backend already rejecting the request correctly (verified via curl: `400 insufficient_balance`, balance and history both left untouched) — the actual gap was purely client-side: the button's `disabled` check only looked at whether fields were filled, never at whether the selected range fit the selected type's balance, so the only way to discover an insufficient balance was to submit and read the resulting error.

Added a purely derived check, computed fresh on every render from state already in scope (`leaveTypes`, `balances`, `logLeaveType`, `logRange`) — no new fetch: a page-local `daysBetweenInclusive()` mirrors `worknest.ts`'s server-side one exactly (same inclusive day-count formula), so what the frontend flags matches what the backend would actually reject, not a looser or stricter approximation of it. `selectedTypeBalance` looks up the chosen type's current balance from `balances`; `exceedsBalance` is `true` once both a type and a range are picked and the computed day count exceeds that balance.

Two effects once `exceedsBalance` is true: a red inline message appears above the submit button (`"Not enough {type} balance — requesting {N} days, {M} available."` — same wording shape as the backend's own `insufficient_balance` message, deliberately, so what you see before submitting matches what you'd have seen after), and **Log leave** itself gets `disabled`, added alongside the existing field-completeness checks rather than replacing them. Nothing about the backend changed — it was already correct; this closes the gap between "the server will reject this" and "the UI tells you that before you find out the hard way."

## Admin balance adjustment (as built)
Direct follow-up once Log leave meant balances could only ever go down: "the admin need to have the option to modify the leave balance of each member." Before building it, explicitly confirmed this is *not* a reintroduction of the removed approval system — direct correction: "there should be not be any approval section from the admin. Its just the info to the team" — so this card has no connection to `leave_requests`, no pending/review concept, and doesn't gate anything Log leave does; it only ever touches balances.

`isAdmin` (`user?.role === 'admin'`) is back in `WorkNestPage.tsx`, used for exactly one thing: gating both the fetch (`useEffect` depends on `isAdmin`, so a non-admin never even issues the `GET /worknest/leave-balances/team` request) and the render of a new **Team leave balances** card at the bottom of the left column. The card is a table — one row per org member, one column per leave type, each cell a `<input type="number">`. Inputs are **uncontrolled** (`defaultValue`, not `value`) with an `onBlur` handler (`handleBalanceEdit`) that fires the `PATCH` — deliberately not a controlled input with a re-render on every keystroke, since nothing needs to react to the in-progress typed value, only the final one once the admin clicks away.

On success, `handleBalanceEdit` updates `teamBalances` in local state directly (no full refetch) so the table reflects the new value without a round trip; if the admin happens to be editing their own balance, it also calls `fetchLeaveData()` so the "Leave balance" stat-tile card above (which reads from the separate caller-scoped `GET /worknest/leave-balances`, not the team endpoint) picks up the change too. On failure, `window.alert(...)` surfaces the error — the same simple pattern the old `handleReview` used for its own PATCH failures, chosen over a more elaborate per-cell error state for a table this small (12 rows × 5 columns at real scale).

**Confirmation went through two rounds of direct follow-up before landing on its current shape.**

Round 1 ("Add a confirmation message for the admin after updating the leave balance for the member"): a single string in an inline `bg-green-50` box at the top of the card — same convention as `ProfileSettingsPage.tsx`'s "Saved." banners.

Round 2 ("it needs to be visible as a pop up message"): replaced with the existing `ConfirmationToast` component (`src/components/ConfirmationToast.tsx`) — this app's established replacement for `window.alert()`-style confirmations, already used by `TasksPage.tsx`. Centered, fixed-position, auto-dismissing (2200ms) dark pill, no page-dimming overlay.

Round 3 ("It should be visible as a pop up window with the modification details"): the toast's single line of text wasn't enough — "details" meant showing the actual before/after values structured, not a sentence summarizing them. Replaced `ConfirmationToast` with a **details modal** built directly in `WorkNestPage.tsx`, reusing `ReasonModal.tsx`'s overlay+centered-card pattern (`bg-ink/25` backdrop, `rounded-2xl bg-white` card, click-outside-to-close) rather than that component itself, since `ReasonModal` is shaped around collecting a text input, not displaying read-only fields. State changed from a single `balanceSavedMessage: string | null` to a structured `balanceUpdate: BalanceUpdateDetails | null`, rendered as label/value rows inside the card, with a **Done** button instead of an auto-dismiss timer — the point of a details modal is giving the admin time to actually read it, not a passing confirmation. `previousBalance` has to be captured from `teamBalances` *before* the `PATCH` fires (same as the member/type names were in round 1) since the `PATCH` response is a bare `204` with nothing to read the prior value back from.

Round 4 ("there should be employee ID in the popup"): added an **Employee ID** row (between Member and Leave type) to the modal. Required a matching backend change first — `GET /worknest/leave-balances/team` didn't select `employee_id` at all — so `TeamMemberBalances` (`app/src/lib/api.ts`) gained an `employeeId: string` field, and `BalanceUpdateDetails` gained the same, populated from `member?.employeeId` at the same point in `handleBalanceEdit` where `memberName` is captured (before the `PATCH`, from `teamBalances` state, same reasoning as `previousBalance`). Rendered as `{balanceUpdate.employeeId || '—'}` — `employee_id` is free text with no default beyond `''` (see `landing-login/backend.md`'s "Employee profile fields"), so a member who's never had one set shows an em dash rather than a blank row that looks broken.

Second pass (Log leave form): `tsc --noEmit` clean. Also verified via curl against a disposable test account (created, tested, deleted — real data never touched) that logging with a `0` balance correctly 400s `insufficient_balance` before any row is written.

**Team on leave**: still verified via curl that `GET /on-leave` returns Ambika's 2 real upcoming approved requests (Sept 2026), sorted ascending, and now also picks up a freshly-logged entry immediately (confirmed with the same disposable test account above). The Dashboard Leave calendar's "See all →" still lands on and scrolls to `#team-on-leave` correctly (see history below for how that scroll race was originally fixed) — unaffected by either pass of this change.

**Admin balance adjustment**: `tsc --noEmit` clean. Verified via curl using the real admin session against a disposable second test member (created, edited, deleted afterward — real data untouched): `GET /leave-balances/team` returned the full real 12×5 grid; `PATCH`-ing the test member's Casual Leave from `0` to `8` returned `204` and the member's own `GET /leave-balances` immediately reflected `8`; the same `PATCH` and the `GET /team` endpoint both correctly `403`'d when attempted from the non-admin test member's own session. The confirmation UI itself (toast, then details modal) is pure client-side rendering with no additional backend surface — `tsc --noEmit` clean is the applicable check for each round, not a separate curl pass. The Employee ID addition (round 4) *did* need a curl check, since it required a real backend change: re-queried `GET /leave-balances/team` with the real admin session and confirmed `employeeId` present on every row (`""` for Ambika, matching her never having set one).

**Insufficient-balance warning**: `tsc --noEmit` clean. Reproduced the reported scenario first — granted a disposable test member an 8-day Casual Leave balance (via the admin balance table's own `PATCH`), then attempted `POST /worknest/leave-requests` for a 12-day range as that member: confirmed via curl the server correctly returned `400 insufficient_balance` with the balance and leave history both left untouched — establishing the backend was never the problem before touching any frontend code. The frontend fix itself is a pure computed value with no network calls, so it doesn't need its own curl verification beyond `tsc --noEmit`; a `balances`-not-yet-loaded window (`selectedTypeBalance` is `null` until the initial `GET /worknest/leave-balances` resolves) is the one moment the button can still be enabled despite an eventual insufficient-balance rejection — narrow enough (a single fetch on page load) not to warrant a loading-guard of its own.

## Known gaps
- No loading skeleton beyond a plain "Loading…" text per card — matches the rest of this app's convention, not a WorkNest-specific gap.
- No cancellation/edit of a logged leave entry from the UI — once submitted, "Leave history" has no delete/undo action for the entry itself (only its associated balance can be corrected afterward, via the admin table — see `worknest/backend.md`).
- `/worknest/payslips` no longer exists at all — see `worknest/backend.md`'s "Payslips — removed" section.
- "Team on leave" only shows *current or upcoming* leave (`to_date >= today`), same as the backend's definition — there's no way to look back at who was out last month from this card.
- The `#team-on-leave` anchor scroll can land short of putting the card at the very top of the viewport when the page is too short to scroll that far — not a bug, just a ceiling imposed by how much content exists below the card.
- `DateRangePicker`'s presets are still backward-looking (`Today`/`Yesterday`/`Last 7 days`/etc.) even though logging leave is almost always for a *future* date range — same known limitation the original Apply-for-leave form had, carried over unchanged since Log leave reuses the same component the same way.
- No audit trail for who changed a balance, from what, to what, or when — see `worknest/backend.md`'s matching gap.
- The `balanceUpdate` details modal only ever shows the single most recent edit — editing a second cell before dismissing the first modal just replaces its contents, there's no queue or history of multiple pending confirmations.
- No keyboard escape (`Esc`) to close the balance-update modal — only clicking the backdrop or the **Done** button dismisses it. Matches every other modal in this app (`ReasonModal.tsx` included) — none of them handle `Esc` either, not a gap specific to this one.
